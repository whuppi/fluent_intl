# Updating fluent_intl

Maintenance recipes for the `package:intl` satellite. For how it's
wired see [`ARCHITECTURE.md`](ARCHITECTURE.md); for capability status
see [`CAPABILITY_ROADMAP.md`](CAPABILITY_ROADMAP.md). Core-side
maintenance (corpus source, option contract, spec tracking) lives in
[`fluent_bundle/docs/UPDATING.md`](../../fluent_bundle/docs/UPDATING.md).

This package tracks three upstreams:

| Source | Why |
|---|---|
| `package:intl` | The rendering engine — every ✗ in the roadmap is its API ceiling |
| CLDR `ordinals.xml` (via `package:intl`'s locale list) | The inlined ordinal rules |
| Mozilla's fluent-rs resolver fixtures | The vendored `test/_corpus/bundle/` copy |

`l10n_currencies` (currency long names) rides along as a fourth, minor
one.

---

## When to update

| Trigger | Recipe |
|---|---|
| `package:intl` releases | §1 — The intl bump review |
| `l10n_currencies` releases | §2 — Standard pub upgrade |
| A CLDR release changes ordinal rules (or intl adds locales) | §3 — Regenerate the ordinal fixture |
| New fluent-rs fixtures | §4 — Refresh the corpus (sync with siblings) |
| A new ECMA option lands in the core | §5 — Wire it here |

---

## §1 — The intl bump review

```sh
fvm dart pub upgrade intl
fvm dart analyze . && fvm dart test
```

Then the ceiling review — intl bumps rarely add formatter API, but when
one does, a ✗ can retire:

1. Read intl's CHANGELOG for new `NumberFormat` / `DateFormat` surface
   (rounding, sign display, calendars, zones — the roadmap's Table 2 is
   the checklist).
2. For each retired ✗: wire the rendering in the right pipeline stage,
   delete the per-call degrade, **flip the `BackendExpectations` flag
   ✗→✓** in `test/conformance_test.dart` — the harness then demands
   the positive check and stops demanding the degrade.
3. Update the roadmap's Table 2 and the family matrix cell in the
   core's CAPABILITY_ROADMAP.
4. New locale data (added locales, changed patterns) can shift expected
   strings in behavioral tests — those are data updates, not
   regressions; verify against intl's own output before touching an
   expectation.
5. Run §3 if the bump changed intl's plural/locale set — the ordinal
   compliance test gates the inlined rules against it.

---

## §2 — Refresh `l10n_currencies`

```sh
fvm dart pub upgrade l10n_currencies
fvm dart test test/number/number_map_test.dart
```

New locales or renamed currencies land automatically —
`currency_name.dart` is a thin lookup.

## §3 — Regenerate the CLDR ordinal fixture

The inlined ordinal rules (`lib/src/plural/ordinal.dart`) are held to
CLDR by an autogenerated fixture. When CLDR revises ordinal rules or
intl's locale list changes:

```sh
# 1. Regenerate — fetches CLDR's ordinals.xml examples and writes
#    test/plural/_cldr_ordinal_examples.dart
fvm dart run tool/regen_cldr_ordinal_fixture.dart

# 2. The gate
fvm dart test test/plural/ordinal_cldr_compliance_test.dart
```

The compliance test enforces three things:

- every CLDR example selects the right category through
  `ordinalCategory` for every supported locale;
- **no orphans** — every inlined locale still exists in CLDR;
- **no gaps** — every CLDR locale with non-trivial ordinal rules is
  inlined (locales whose rules are `other`-only need no entry).

A gap failure means hand-porting the new locale's rules into
`ordinal.dart` from the CLDR rule text the tool prints. Never shrink
the test to pass.

---

## §4 — Refresh the fluent-rs corpus

`test/_corpus/bundle/` is one of THREE pinned copies (core's syntax
fixtures + both satellites' resolver fixtures). They refresh together,
same session, same upstream commit — the recipe and the sync-together
rule live in the core's
[`UPDATING.md`](../../fluent_bundle/docs/UPDATING.md) §1. Never refresh
this copy alone; never hand-edit a vendored fixture. Bump
`test/_corpus/PROVENANCE.md` with the new commit.

---

## §5 — Wire a new ECMA option

The end-to-end recipe (value field → builtin validation →
resolveDigits → satellite → harness flag → roadmap row) is the core's
[`UPDATING.md`](../../fluent_bundle/docs/UPDATING.md) §2. The
intl-side step:

1. Can intl render it? Wire it through `builder.dart` (numbers) or
   `datetime_map.dart` — and **into `optsKey` / the datetime cache
   key** if it affects construction. Both cache-collision bugs this
   family has had were missing key fields; `number_map_cache_test.dart`
   is where the regression row goes.
2. Can't render it? Per-call `FluentTypeError.unsupportedOption` in the
   router (never inside a cached builder), flag `false` in
   `conformance_test.dart`, row in the roadmap's Table 2.

## Reading the failure modes

| Failure | First check |
|---|---|
| Conformance fails after an intl bump | Either a ✗ silently retired (degrade check fails because the option now renders — flip the flag, §1 step 2) or intl changed output for a ✓ check — diff against intl's changelog. |
| Ordinal compliance fails | CLDR moved or intl's locale list changed — §3. A "gap" failure is a new locale to hand-port, not a test to shrink. |
| Corpus fixture fails | Same triage as the core's §1: new spec feature vs regression. Confirm the sibling copies are on the same commit first. |
| Two option bags render identically when they shouldn't | Missing `optsKey` field — add it + a `number_map_cache_test.dart` row. |
| A combined date+time is mis-ordered in some locale | Skeleton-string concatenation crept in — compose with `add_*` (see ARCHITECTURE §2). |
